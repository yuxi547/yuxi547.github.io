01

Why

Our goal is a robot that can finish long, compound tasks and gets better at them the more it runs. Neither comes easily today.

1.1  Why an agentic robot

Coding agents finish long tasks by writing, running, reading the result and fixing it. A robot can work the same way.

The problem

Vision-language-action policies (VLA) and world-action models (WAM) now do single short motions well. A long, compound task is still hard for them. Such a task asks for more than motion: watch a sorting sequence and repeat it from memory, solve an equation and place the answer, pick the object a sentence describes, play tic-tac-toe, check at the end that every condition holds.

An end-to-end policy has to think and move in the same forward pass, many times a second. An early mistake carries through everything after it, and there is no point at which the policy stops to check.

The idea

The digital world had the same problem and found a way through. A coding agent does not produce the answer in one pass. A general-purpose model writes a piece, runs it, reads what came back and fixes it, and with tools and that loop it finishes long tasks. We set out to bring this way of working to robots.

What had been missing was a general model that understands a physical scene. GPT-6 Astra changed that: its early evaluations in embodied reasoning and manipulation showed that a general model can drive a robot. That sped everything up.

The architecture

So the system has three layers.

System 2 is a foundation model: it splits a long task into sub-tasks. Any capable model can sit here.

System 1 is skills and tools, which carry out each sub-task. This layer is open. The classical stack plugs in directly: object detection, segmentation, SLAM with path planning, visual servoing. A VLA or a WAM can be wrapped as a skill and called like any other.

System 0 is motion planning and control, which turns the target a skill asks for into joint motion.

The three together are what we call an agentic robot. It does not replace VLAs. The short motions a VLA is good at become one skill among others, and the long part goes to System 2.

This preview

HyperBrain-RSI-Preview is the first version of this architecture. The foundation model is Claude Opus 5.5. The skill layer holds segmentation, measurement from pixels and a few Python tools per task. Motion is planned by cuRobo.

Even this much buys three things. A new task is a few paragraphs of notes and a few Python functions, not a new set of demonstrations and a training run; the same model and primitives run all 54 task configurations, and the benchmark's demonstrations are read while the notes are written but no network is trained on them. A failed episode leaves its programs, its reasoning and the numbers it measured, so the log shows the line that went wrong, where a failed policy rollout leaves a video. And the base model is a setting in a configuration file: when a stronger one appears, nothing is collected again or retrained.

The open question

Who writes the notes and tools each task needs? That is where the second idea comes in.

1.2  Why self-improvement

The bottleneck is not intelligence. It is experience with this particular body, and experience only comes from acting. So something has to turn run logs into knowledge.

A general model knows what a tower is and can plan how to build one. It does not know how an object hangs in this gripper, how deep this simulator wants a button pressed, or how often these arms refuse a move. The lines on the right are from the prompt the executor agent runs with today.

None of this can be reasoned out from first principles. Each line is there because an episode ran into it.

From the prompt

A held object hangs below the fingers: gripped by a rim it tilts (about 40 degrees in our runs) and its lowest point sits about 0.7 of its width below the TCP.

Press, strike, push and insert past first contact: aim about 1 cm beyond the measured contact surface […] Stopping at the surface does not register.

About one move or move_both in ten fails without moving (unreachable, no_line, collision).

Those lines live in the harness. The model's weights sit behind an API. Everything else in the agent is the harness, and all of it is plain text and Python. It has three parts: the runtime (the loop that calls the model, the sandbox that runs its programs, the interface to the simulator, the logs), a part shared by every task (the handbook, the skills, the motion primitives), and for each task its notes and tools.

  1. Facts about a body are found by trying. The model has to be told them, and someone has to find them out first, by running into them.
  2. Text and code are what can change, and what a language model writes best. Since the logs are readable and the harness is writable, the one who reads the failures and writes the next version can be a language model too.
  3. Writing it by hand does not scale. There are 54 configurations, and each fails in its own ways.
  4. Every change can be tested. A new version is compared with the current one on the same ten layouts, and it is kept only if it scores higher. The final score is measured on a seed that no round ever ran.

We call the one that acts the executor agent and the one that rewrites its harness the optimizer agent. It rewrites only the third part, each task's notes and tools. The first two are written by hand.

Written down, the loop is three lines, or a dozen lines of pseudocode:

An=Agent(F, Hn)
Δn=Improve(Hn, Ln)
Hn+1=Hn⊕ΔnifV(Hn⊕Δn)>V(Hn)

Run. Read the logs. Rewrite the harness. Keep it only if it scores higher.

Improve = read → edit → check → validate → keep or drop.

F never changes, so any change in score comes from H. One task shows what that looks like. In build_tower the executor agent stands four pillars, lays boards across them and sets a roof on top.

Round 3 made the executor agent faster: both grippers opening and closing at once, full speed, and the cheaper of two equivalent wrist turns. It solved one layout that round 2 had lost and lost two others, so the rule dropped it. Reading its failures showed why the pillars fell: two open grippers coming down over them while the wrists were still turning swept them over. Round 4 kept the speed and added tools that place the boards and the roof. It solved all ten validation layouts.

Across the whole benchmark, the starting version of the harness scored 38.9 on the training layouts (ten per configuration) and the final one 78.87 on the test seed, with the same base model throughout.

Who does the improving. The optimizer agent, not a person. It is Claude too, and it reads the logs of each batch, finds what caused the failures and edits the task's notes and tools.

1.3  Why RoboDojo

RoboDojo is where we test this first version. Its 42 simulation tasks cover precision, long-horizon, memory, open instructions and generalization, which are the long, compound tasks this section started from. Trained policies and agents are scored by the same script and ranked on one public leaderboard. And because it is a simulator, the next version can be run on exactly the same layouts, with separate seeds for developing and for reporting.

02

Method

An episode is the executor agent at work: a conversation between the model and a Python session. The model writes a program. The session runs it against the robot and returns what the program printed, plus the camera images it asked for. That is all the model knows when it writes the next one.

2.1  Programs, not actions

The model never outputs an action. Each call writes a program that chains many motions, tests every result and stops at the first failure.

A model call takes seconds and a control step lasts 40 ms, so the model cannot be asked what to do at every step. In one stack_blocks episode the robot took 515 steps, and the model was called 6 times.

Every primitive returns whether it worked and an error code, so the next decision starts from what happened, not from what was planned. Looking and measuring use no environment steps, only motion does, so a program measures first and then chains the motions. And when an episode fails, there is a line where it failed.

2.2  Measure, don't assume

Every position is measured during the episode from three RGB cameras. There is no depth image and there are no object models.

One view gives a ray, which fixes a point only on a known plane such as the table top. Two views give a point when every ray passes within 3 mm of it and the rays cross at 10° or more. Below 10°, one pixel of matching error already costs more than a centimetre.

A failed measurement is still an answer. It comes with the spot to look at, and the model moves a wrist camera over it and asks again.

2.3  Improve what you can read

The weights never change. Between rounds the optimizer agent rewrites only a task's notes and tools, and a change is kept only if it scores higher.

Notes hold what a general model could not have known beforehand: each line is something an episode ran into. When a lesson is a procedure, it becomes a tool, ordinary Python on the same primitives.

An edit may touch only its own task, and a tool may not branch on a task's name, since one executor agent runs all 54 configurations. Rounds run on seeds 0 and 1. The scores we report are from seed 2, which no round touched.

Results

Self-reported. We ran the benchmark's own script on seed 2 ourselves: 2,100 episodes over all 54 configurations, with the notes and tools frozen before the run.

Score / success rate, in the columns of the RoboDojo sim leaderboard. Generalization is the mean of the standard and random variants, and Average is the mean of the five dimensions. Generalization tasks run 25 layouts per configuration, the others 50. Runs completed before RoboDojo published its new Agent Track rules on November 14.

The executor agent is strongest where a task is mostly deciding (Memory, 96.17) or places rigid objects exactly (Precision, 91.08). 24 of the 54 configurations score 90 or more.

It is weakest on the two Generalization groups, at 52.37 and 50.00. They hold most of the tasks with cloth, handovers and objects that slide when touched.

It is cheap to run. The 2,100 episodes cost $1,219.51 in model calls, about $0.58 each. By our estimate from what they have published, other agents on the board spend roughly $1 to $2.5 per episode. Three things keep it low. One call writes a program that runs for many steps, so an episode needs few calls (section 2.1). Positions are measured locally and come back as numbers, and the model is shown only the images from its last three looks plus up to three it chooses to keep, so images do not pile up in the conversation. And the prompt and the earlier turns are read from the cache on every call. The improvement rounds that produced the notes and tools cost about $2,300 in model calls.
